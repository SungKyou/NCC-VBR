# 검증 절차

전환본이 원본과 같은 일을 하는지 확인하는 방법이다. 검증 수준, 실행 방법, 결과를 적는 표현, 증거 보관 규칙을 정한다.

## 1. 검증 수준

검증은 다섯 수준으로 나눈다. 아래 수준이 통과해야 위 수준으로 간다.

| 수준 | 이름 | 확인하는 것 | 실행 환경 | 이번 프로젝트의 수단 |
|---|---|---|---|---|
| V0 | 정적 검사 | 빌드, 형식, 정적 분석 오류가 없다 | 개발 PC | `gofmt -l`, `go vet` (Windows, Linux 대상 각각) |
| V1 | 단위 시험 | 기능 하나하나가 요건대로 동작한다 | 개발 PC, Linux | `go test ./...` |
| V2 | 원본 비교 시험 | 원본과 전환본이 같은 입력에서 같은 결과를 낸다 | 원본을 컴파일할 수 있는 Linux | `go/test/parity/` (컨테이너에서 원본 C를 컴파일해 실행) |
| V3 | 통합 시험 | 실제 연결 대상(NAS 마운트, 포털, 호출하는 관리 프로그램)과 함께 동작한다 | 시험 서버 | 사용자 실행. 절차는 서비스별 `06` 문서 |
| V4 | 운영 규모 시험 | 실제 자료 규모에서 시간과 자원 사용이 받아들일 만하다 | 시험 서버 또는 운영과 같은 환경 | 사용자 실행. 절차는 서비스별 `06` 문서 |

전환 후 병행 운영(원본과 전환본을 함께 실행해 비교)은 검증이 아니라 전환 단계의 일이다. `07` 문서에 적는다.

## 2. 수준별 실행 방법

### V0. 정적 검사

```powershell
cd c:\dev\ncc-vbr-go\go
gofmt -l .                      # 출력이 없어야 한다
go vet ./...                    # Windows 대상
$env:GOOS='linux'; go vet ./...; Remove-Item Env:GOOS   # Linux 대상
```

### V1. 단위 시험

Windows에서 실행한다.

```powershell
cd c:\dev\ncc-vbr-go\go
go test ./...
```

Linux에서 실행한다. 개발 PC에 Go가 설치된 Linux가 없으면 Windows에서 Linux용 시험 실행 파일을 만들어 WSL에서 돌린다.

```powershell
cd c:\dev\ncc-vbr-go\go
$env:CGO_ENABLED='0'; $env:GOOS='linux'; $env:GOARCH='amd64'
foreach ($p in 'cifs','remove','config','logx','portal') { go test -c -o bin/linux-test/$p.test ./internal/$p }
Remove-Item Env:GOOS, Env:GOARCH, Env:CGO_ENABLED
wsl -d Ubuntu -- sh /mnt/c/dev/ncc-vbr-go/go/test/run-linux-tests.sh
```

Linux에서만 실행되는 시험이 있다(파일 접근 시각 규칙, 심볼릭 링크). Windows 결과만으로 통과를 판정하지 않는다.

### V2. 원본 비교 시험

원본 C 소스를 고치지 않고 컴파일해, 전환본과 같은 입력으로 실행하고 결과를 비교한다. 이 수준이 "원본과 같다"는 판정의 주된 근거다.

```powershell
cd c:\dev\ncc-vbr-go
go\build.ps1 linux
docker build -f go/test/parity/Dockerfile -t ncc-vbr-parity .
docker run --rm ncc-vbr-parity
```

비교 방법은 다음과 같다.

1. 원본과 전환본에 각각 작업 디렉터리를 만들고 같은 원본 디렉터리 구조와 설정 파일을 넣는다.
2. 같은 순서로 실행한다(첫 실행, 변경 후 실행, 변경 없이 실행, 삭제 LOG 모드, 삭제 DELETE 모드).
3. 실행마다 대상 디렉터리의 구조, 파일 내용 체크섬, 이전 버전 파일을 풀어낸 내용, 로그의 합계 숫자, 삭제 명령 목록을 비교한다.
4. 실행 시점마다 달라지는 값(이전 버전 파일 이름의 시각, 작업 디렉터리 이름)은 가리고 비교한다.

비교 시험을 새로 만들 때 지킬 점이다.

- 원본 소스는 고치지 않는다. 컴파일 옵션을 더했으면 이유를 Dockerfile에 적는다.
- 변경 대장에서 "동작을 바꿨다"고 한 항목은 비교 대상에서 빼거나 따로 판정한다. 뺀 항목은 시험 문서에 적는다.
- 원본이 멈출 수 있으므로 대기 시간에 상한을 둔다.
- 시험 스크립트 자체가 틀릴 수 있다. 처음 실패하면 프로그램을 고치기 전에 원본·전환본 어느 쪽 결과가 요건과 맞는지부터 본다.

### V3. 통합 시험, V4. 운영 규모 시험

개발 PC에서 할 수 없는 시험이다. 서비스별 `06` 문서에 절차와 기록 양식을 둔다. 사용자가 실행하고 결과를 그 문서에 적는다.

## 3. 시험 설계 기준

요건 하나에 시험이 하나 이상 연결되어야 한다. 시험을 만들 때 다음 경우를 빠뜨리지 않는다.

| 분류 | 확인할 경우 |
|---|---|
| 정상 | 대표 입력에서 요건대로 동작한다 |
| 경계 | 빈 디렉터리, 이름에 공백이 있는 항목, 개수·길이 한도, 기준 시각과 같은 값 |
| 반복 | 같은 입력으로 다시 실행했을 때 결과가 바뀌지 않는다 |
| 오류 | 대상 없음, 쓰기 실패, 권한 없음, 설정 항목 없음, 잘못된 인자 |
| 원본 결함 | 변경 대장의 결함마다, 고친 것은 고쳐졌는지, 유지한 것은 원본과 같은지 |
| 자료 보호 | 지우거나 덮어쓰는 기능은 대상이 아닌 자료를 건드리지 않는다 |
| 운영체제 | 대상 운영체제마다 실행한다. 한쪽에서만 되는 시험은 건너뜀으로 기록된다 |

## 4. 증거 보관

- 실행 출력은 고치지 않고 `docs/evidence/`에 저장한다.
- 실패한 실행도 지우지 않는다. 실패 원인이 프로그램인지 시험인지 환경인지 시험 문서에 적는다.
- 파일 이름은 `수준-환경.txt` 또는 `수준-run-번호.txt`로 한다.
- 시험 문서에는 실행한 날짜, 실행한 명령, 도구 버전, 증거 파일 이름을 적는다.

## 5. 판정 표현

결과를 적을 때 다음 표현만 쓴다. 뜻이 다른 표현을 섞지 않는다.

| 표현 | 뜻 |
|---|---|
| 통과 | 이번에 실행했고 기대한 결과가 나왔다. 증거 파일이 있다 |
| 실패 | 이번에 실행했고 기대와 달랐다 |
| 건너뜀 | 시험이 그 환경에서는 실행되지 않도록 만들어져 있다(예: Windows에서 심볼릭 링크 시험) |
| 미실행(사유) | 실행하지 못했다. 사유와 재개 조건을 함께 적는다 |
| 정적 확인 | 실행하지 않고 소스를 읽어 확인했다 |

서비스 전체의 판정은 다음 가운데 하나로 쓴다.

| 판정 | 조건 |
|---|---|
| 개발 검증 통과 | V0, V1, V2가 통과했다 |
| 운영 전환 가능 | V3, V4까지 통과했고 변경 대장의 결정 대기 항목이 없다 |
| 보류 | 실패가 남았거나, 필수 수준을 실행하지 못했거나, 결정 대기 항목이 있다 |

과거에 통과한 기록을 지금도 통과한다는 뜻으로 쓰지 않는다. 소스를 고쳤으면 관련 시험을 다시 실행하고 날짜를 새로 적는다.

## 6. 결함이 나왔을 때

1. 증거 파일을 보관한다.
2. 원인을 분류한다. 전환본 결함, 시험 결함, 환경 문제, 원본 결함(전환본이 원본과 다르게 옳게 동작).
3. 전환본 결함이면 고치고 관련 단위 시험을 더한 뒤 그 수준부터 다시 실행한다.
4. 원본 결함이면 변경 대장에 결함으로 올리고 처리 방침을 정한다.
5. 같은 원인을 세 번 고쳐도 해결되지 않으면 멈추고 보고한다.
