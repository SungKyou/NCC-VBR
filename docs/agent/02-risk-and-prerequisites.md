# agent 위험과 사전 확인 사항

기준일: 2026-11-17 / 근거: [01-asis-preliminary.md](01-asis-preliminary.md)의 읽은 범위 / 양식: T08

사용자 지시 4번("전환에 시간이 많이 걸리거나 문제가 있으면 작업 이전에 알려 달라")에 대한 보고다.

## 1. 요약

- 전환할 수 있는가: **조건부 가능**. Go로 옮기는 데 기술적으로 막히는 것은 없다. 조건은 시험 환경(XenServer)과 상대 프로그램의 전문 정보다.
- cifs·remove와 다른 점: 한 번 실행하고 끝나는 배치가 아니라 상주 데몬이다. 스레드 15개 안팎, 메시지 큐 7개, 공유 메모리, 보조 프로그램, 외부 명령 15종이 얽혀 있다. 원본 줄 수는 cifs의 4배다.
- 가장 큰 위험 세 가지
  1. 개발 PC에는 XenServer가 없다. 백업·복구·조회의 실제 동작을 여기서 확인할 수 없다(R-AG-01).
  2. 요청을 보내는 관리 서버의 소스가 없다. 응답 전문이 byte 단위로 맞아야 하는데 기준이 원본 소스뿐이다(R-AG-02).
  3. 네트워크로 받은 문자열이 셸 명령에 그대로 들어간다. 그대로 옮기면 취약점도 옮겨지고, 고치면 동작이 달라진다(R-AG-03).
- 구현 전에 정해야 하는 것: 8건(Q-A01~Q-A08).
- 좋은 소식: `dummy2.c`를 받아 보조 프로그램의 동작을 확인했다. Go에서는 "제한 시간이 있는 명령 실행"으로 프로세스 안에 들어가고, 보조 프로그램과 메시지 큐 30001이 없어진다. 원본 agent는 가짜 `xe` 명령을 만들어 주면 컨테이너에서 실행할 수 있어, cifs처럼 원본 비교 시험을 만들 수 있다.

### 3.1 원격 실행(agentless) 검토 (2026-11-17, Q-A09 재검토)

얻는 것

| 항목 | 내용 |
|---|---|
| 설치 | dom0에 아무것도 설치하지 않는다. 호스트 업데이트·재설치 뒤 agent를 다시 설치하는 일이 없어진다 |
| 보안 | 인증 없는 셸 실행 포트(R-AG-03)가 dom0에서 사라진다 |
| 재사용 | ncc-xen의 XAPI 세션, 풀 마스터 전환 처리, `/export`·`/import`와 진행률, 작업 취소, dom0 SSH 진단(`internal/hostssh`)을 그대로 참고할 수 있다 |
| 배포·운영 | cifs·remove와 같은 서버, 같은 설치·로그·교체 절차. 병행 운영과 되돌리기가 쉽다(dom0를 건드리지 않는다) |
| 공유 메모리·`fuser`·`ps` | 원격에서는 쓸 일이 없어져 Q-A04·A05가 단순해진다 |

달라지는 것과 대응(전문을 바꾸지 않는 (나-1) 기준)

| 원본 동작 | 원격 실행에서 생기는 일 | 대응안 | 결정 |
|---|---|---|---|
| 관리 서버가 호스트마다 그 호스트의 agent에 접속 | agent 서버 하나가 여러 호스트를 맡는다 | 호스트마다 수신 포트 하나를 열고 설정으로 포트 ↔ 호스트를 묶는다. 관리 서버는 접속 IP·포트만 바꾼다 | 관리 서버가 agent IP를 호스트 IP로 다른 곳에도 쓰는지 확인 필요 |
| `S` 동기 명령 = dom0 셸 | 원격에서는 dom0가 아니다 | (가) SSH로 dom0에서 실행(ncc-xen `hostssh` 방식, root 암호 = XAPI 암호) (나) 지원 중단 | 관리 서버가 `S`를 무엇에 쓰는지(표본은 `df -k /`) 확인 필요 |
| `STATUS`의 dom0 CPU·메모리·디스크 | XAPI에 dom0 디스크 사용률이 없다(ncc-xen `hostssh` 주석에 실측 기록) | CPU·메모리는 XAPI 지표(RRD, host metrics), 디스크는 SSH | 값의 계산 방식이 `sar`·`free`와 달라진다 → 변경 대장 |
| 백업 파일 경로 `/BACKUP/…`, `DIR-INFO` | dom0가 아니라 agent 서버의 경로가 된다 | agent 서버에 같은 NAS를 같은 경로로 마운트하면 전문은 그대로 | NAS 마운트 계획 |
| 백업 자료 흐름 | 지금: dom0 → NAS. 원격: 호스트 → (HTTPS) → agent 서버 → NAS. 네트워크를 두 번 지나고 TLS 비용이 든다 | agent 서버를 NAS와 같은 망에 두고 대역폭을 잰다. 필요하면 압축을 XAPI(`use_compression`)에 맡긴다 | 백업 시간대 안에 끝나는지 실제 풀에서 측정(V4) |
| 복구(`RESTORE`) | 파일을 agent 서버가 읽어 호스트로 올린다 | ncc-xen의 가져오기 방식 | 같은 측정 |
| `RES-VM-INFO`, 이벤트의 `host_name` | "agent가 떠 있는 호스트"가 없다 | 포트에 묶인 호스트로 정한다 | (나-1)이면 해결 |
| 상태 감시의 "XenServer Fail" | XAPI 장애와 네트워크 장애를 구분하지 못한다 | 이벤트 문구는 그대로 두고 로그에 원인 구분 | - |
| 자격 증명 | 원본은 필요 없었다 | 풀 root 암호를 agent 서버에 암호화해 둔다(ncc-xen `stdcrypto` 참고) | 보관 방식 결정 |
| 의존 라이브러리 | cifs·remove는 표준 라이브러리만 쓴다 | SSH를 쓰면 `golang.org/x/crypto/ssh`가 필요하다 | 표준 구조(`common/02`)의 의존 규칙에 예외 추가 |

조건(이것이 확인되면 (나-1)로 확정할 것을 권한다)

1. 관리 서버(ASP)가 agent의 접속 주소를 설정에서 바꿀 수 있고, 그 주소를 다른 용도(호스트 식별 등)로 쓰지 않는다.
2. 관리 서버가 쓰는 `S` 명령 목록. SSH로 옮길지 없앨지 정한다.
3. agent 서버에 백업 NAS를 마운트할 수 있다.
4. 시험 풀에서 큰 VM 하나의 내보내기 시간을 dom0 방식과 원격 방식으로 비교한다(A7 전에 미리 측정 권장).

## 4. 시험할 수 없는 것

| 대상 | 필요한 환경 | 대신 할 수 있는 것 |
|---|---|---|
| 실제 스냅샷, 내보내기, 가져오기 | XenServer 풀과 시험용 VM | 가짜 `xe`로 명령 순서와 인자, 실패 때의 정리 순서를 원본과 비교 |
| 실제 `xe` 출력 읽기 | 대상 버전의 XenServer | 받은 출력 표본을 가짜 `xe`에 넣어 원본과 비교 |
| 큰 XVA 파일 검증 시간 | 실제 백업 파일 | 작은 XVA 파일(직접 만든 tar)로 판정 결과만 원본과 비교 |
| 관리 서버와의 연동 | 관리 서버 | 전문을 보내는 시험 프로그램으로 원본과 응답 비교 |
| 장시간 작업 중 재기동 | 실제 풀 | 가짜 `xe`를 오래 걸리게 해서 재기동 뒤 상태 비교 |
| dom0 자원 사용 | 실제 dom0 | 없음 |

2026-11-17 갱신(Q-A01 = XAPI): 조회 구간은 `xe` 출력 읽기 대신 XAPI 호출과 값 대응표가 일이 된다. 분량은 비슷하다. 백업·복구는 ncc-xen의 내보내기·가져오기(`internal/job/vm_backup_export.go` 432줄, `vm_backup_restore.go` 435줄)를 참고할 수 있어 줄어든다. 대신 XAPI 클라이언트 이식(`pkg/xapi` 약 1,150줄 + 쓰는 부분의 mixin)과 가짜 XAPI 시험 기반이 새로 생긴다. 부분 백업(스냅샷에서 고르지 않은 디스크 지우기)은 ncc-xen의 XVA 내보내기에 디스크 고르기가 없어 새로 만든다(ncc-xen의 OVF 경로는 디스크별로 내보내지만 파일 형식이 XVA가 아니다).

전체 분량은 cifs와 remove를 합친 것의 3배쯤이다. 한 번에 옮기지 않고 [03-conversion-plan.md](03-conversion-plan.md)의 구간으로 나눠 구간마다 원본과 비교하며 진행하는 것을 권한다.
